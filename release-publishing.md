# Release & Commit Methodology — `xpertss/projen` (`@xpertss/projen-types`)

## Scope

This document defines the commit and release discipline required for the `release` workflow (`.github/workflows/release.yml`, generated by projen from `.projenrc.ts`) to publish correctly to npm and GitHub Releases.

Keying requirement: **the first line of your commit message is the release control plane.** Everything else (triggering, versioning, publishing) is automatic once commits follow this spec.

Key words "MUST", "MUST NOT", "SHOULD" are to be interpreted as described in RFC 2119.

## 1. Release triggering

- **Any push to `main`** starts the `release` workflow — direct push or merged PR, both are equivalent. There is no per-release approval step; every push to `main` is a release *attempt*.
- The workflow can also be started manually: Actions → `release` → **Run workflow** (optional `dry_run` input; when true, everything runs except the actual `npm publish`).
- A push that produces nothing releasable (see §3) is a **no-op run**: green, no tag, no npm publish, no GitHub release. This is expected behavior, not an error.

## 2. Commit message rules (MUST)

### 2.1 Format

Commit messages MUST use the [Conventional Commits](https://www.conventionalcommits.org/) format. Only the **first line (subject)** is parsed, in the form:

```
type(scope)!: description
```

- `type` — required, lower-case, from the table in §2.2.
- `scope` — optional, free-form (e.g. `fix(parser): ...`).
- `!` — optional breaking-change marker, see §2.3.
- `description` — imperative mood preferred ("add", not "added"/"adds").

### 2.2 Types and their effect on the version

| First line starts with | Bump level | Example `0.0.0` → |
|---|---|---|
| `feat:` | **minor** | `0.1.0` |
| `fix:` | **patch** | `0.0.1` |
| `perf:` | **patch** | `0.0.1` |
| any type + breaking marker (§2.3) | **major** | `1.0.0` |
| `chore:`, `docs:`, `style:`, `refactor:`, `test:`, `build:`, `ci:` | **none** | (no bump) |
| anything else / no prefix | **none** | (no bump) |

### 2.3 Breaking changes

A change that is incompatible with existing consumers MUST be marked explicitly, one of:

- `!` directly before the colon: `feat!: drop legacy option`
- or a `BREAKING CHANGE:` paragraph in the commit **body** (for any type).

Unmarked breaking changes are the one real hazard in this scheme: they will silently ship as a minor/patch bump.

### 2.4 Examples

| Message | Effect |
|---|---|
| `feat: add Java project scaffold` | minor bump |
| `fix: correct dependency range in .projenrc.ts` | patch bump |
| `feat!: remove deprecated option X` | major bump |
| `Updated the README` | no bump — shipped in the next releasable window, listed under "Other" in release notes |
| `one more fix` | no bump — contains the word "fix" but has no `fix:` prefix |

## 3. Versioning model (verified behavior)

Verified against projen 0.103.23 (`lib/release/bump-version.js`) and `commit-and-tag-version@^12` (the bump engine in the `bump` task, `.projen/tasks.json`).

1. **Baseline** = the latest release tag on `main` (`vX.Y.Z`). The window being evaluated = all commits after that tag.
2. **First release (no tag exists) never bumps** — by design it tags and publishes the version currently in `package.json` (this project: `0.0.0`).
3. **Subsequent releases** bump according to the *highest* level present in the window: major > minor > patch. `feat:` + `fix:` in the same window → minor.
4. **No releasable commits in the window → `bump: "none"`** → the `check_tag_exists` gate (`release.yml`) skips both publish jobs → no-op run.
5. Version numbers are owned by the release toolchain. `package.json` `version` is written by the bump step and restored afterwards (`unbump`); the working copy must never show a drifted version.
6. The bump step is skipped entirely when the latest commit on `main` is `chore(release): ...` (the auto-generated release commit) — releases do not self-trigger.

### 3.1 What non-conventional commits do

Commits without a recognized prefix:

- do **not** trigger a release,
- do **not** bump the version,
- are **not** lost — they are shipped in the next release that the window produces (all commits since the last tag are published together),
- appear under an **"Other"** heading in the generated release notes instead of "Features"/"Bug Fixes".

## 4. Release lifecycle (what CI does per run)

Per push to `main`, in order:

1. `release` job runs `npx projen release` = `rm -fr dist` → **bump** (resolve latest tag → suggest bump from window → apply: new version in `package.json`, tag, changelog to `dist/changelog.md`) → **build** (jsii) → **unbump** → `git diff` must be clean. A build failure aborts the run before anything is published.
2. Gates: `tag_exists` (is `dist/releasetag.txt`'s tag already on origin?) and `latest_commit == github.sha` (did someone push a newer commit mid-run?).
3. If gated through, `Publish to npm` and `Publish to GitHub Releases` run in parallel:
   - **npm:** `publib-npm` with `NPM_TRUSTED_PUBLISHER=true` (OIDC, no token; see `spec/npm-publishing-setup.md`). A version that is already on the registry is reported as `SKIPPING: already published` — green, not an error.
   - **GitHub:** `gh release create vX.Y.Z --target <sha>` with the generated changelog as body; this also creates/pushes the `vX.Y.Z` tag.
4. The `chore(release): vX.Y.Z` commit (author `github-actions[bot]`) lands on `main`.

## 5. Rules

### MUST

- Prefix every user-facing change with `feat:` (new capability) or `fix:` (bug fix); `perf:` for performance fixes.
- Mark breaking changes with `!` or a `BREAKING CHANGE:` body paragraph.
- Use the imperative mood in the subject.
- Verify after each release: `npm view @xpertss/projen-types version` and the GitHub **Releases** page.

### MUST NOT

- Edit `package.json` `version` by hand, or add a `version` field to `.projenrc.ts` — the release toolchain owns version numbers.
- Move, rename, or rewrite release tags (`vX.Y.Z`) on `main` — the tag is the version baseline.
- Force-push `main` — it desyncs the tag baseline from history.
- Edit `.github/workflows/release.yml` directly — edit `.projenrc.ts` and run `npx projen`. In particular, renaming the workflow file or changing the `release_npm` job would orphan the npm **trusted publisher** configuration (see `spec/npm-publishing-setup.md`, step 3).
- Rely on non-prefixed commits to trigger or bump a release.

### SHOULD

- One logical change per commit; keep the subject ≤ 72 chars.
- If merging via PR, use **squash merge** and make the *squash title* the conventional message — it replaces all underlying commit subjects, so a PR full of `feat:` commits merged as "stuff" releases nothing.
- Batch work so each window ends with at least one prefixed commit, if the window contains releasable work.

## 6. Edge cases and known behaviors

| Situation | Outcome |
|---|---|
| Push with only non-prefixed commits | no-op run (green, nothing published) |
| `feat:` + `fix:` in one window | minor bump (highest wins) |
| Re-running the workflow for the same version | `tag_exists` gate skips publishing |
| Version already on npm (e.g. published manually beforehand) | `publib-npm` prints `SKIPPING: already published`, job is green |
| Two pushes in rapid succession | concurrency group serializes; the second run's `latest_commit` gate handles drift |
| Build fails | run aborts, no tag, no publish — push a fix and re-push |
| `chore(release):` is the latest commit | bump step skips — no double release |
