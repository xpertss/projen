# Release & Commit Methodology — `xpertss/projen` (`@xpertss/projen-types`)

## Scope

This document defines how to trigger a release of `@xpertss/projen-types` and the commit discipline required for a release to happen. It applies to the `release` workflow (`.github/workflows/release.yml`, generated by projen from `.projenrc.ts`).

**A release happens when a run of the `release` workflow finds at least one releasable commit since the last release tag** — a commit whose subject is typed `feat:` or `fix:` (see §2). Runs are started by any push to `main` (or manually, §1). A run whose window contains no `feat:`/`fix:` commits is a **green no-op** that publishes nothing — `docs:`, `ci:`, `chore:`, and other commits never release on their own.

Key words "MUST", "MUST NOT", "SHOULD" are to be interpreted as described in RFC 2119.

## 1. Triggering a release

- **Any push to `main`** starts the `release` workflow — direct push or merged PR. The run publishes only if the window since the last release tag contains a releasable commit (below); otherwise it is a no-op.
- The workflow can also be started manually: GitHub → **Actions** → `release` → **Run workflow** (optional `dry_run = true` runs everything except the actual `npm publish`) — useful for re-running after a failed build or to confirm a no-op window.
- At start of the run, the toolchain lists the **releasable commits** between the last release tag (`vX.Y.Z`) and `HEAD`: all non-merge commits whose subject matches `feat:` or `fix:` (with an optional scope and an optional `!`, e.g. `feat(parser)!: ...`).
  - **≥ 1 releasable commit** → the run bumps the version, builds, and publishes to npm and GitHub Releases.
  - **0 releasable commits** (e.g. only `docs:`, `ci:`, `chore:`, or unprefixed commits in the window) → the run is a **no-op**: green, no tag, no npm publish, no GitHub release. This is expected behavior, not an error.

## 2. Commit message rules

### 2.1 Format

Commit messages MUST use the [Conventional Commits](https://www.conventionalcommits.org/) format. Only the **first line (subject)** is parsed for the type, in the form:

```
type(scope)!: description
```

- `type` — lower-case; `feat` or `fix` makes the commit releasable (see §1).
- `scope` — optional, free-form (e.g. `fix(parser): ...`).
- `!` — optional breaking-change marker, see §2.3.
- `description` — imperative mood preferred ("add", not "added"/"adds").

### 2.2 Releasable types and the version bump

Only `feat:` and `fix:` commits are releasable. When a release run does release, the bump level for the window is:

| Window since last tag | Bump level | Example `0.1.0` → |
|---|---|---|
| Breaking change present (§2.3) | **major** | `1.0.0` |
| Else any `feat:` commit | **minor** | `0.2.0` |
| Else (only `fix:` commits) | **patch** | `0.1.1` |

Within one window, the highest level wins.

**All commits since the last tag are included in the release**, not only the releasable ones — `docs:`, `ci:`, `chore:`, and other commits appear in the generated release notes (under an "Other" heading) and are part of the released content. They simply do not, on their own, cause a release to happen.

### 2.3 Breaking changes

A change that is incompatible with existing consumers MUST be marked explicitly, one of:

- `!` directly before the colon: `feat!: drop legacy option`
- or a `BREAKING CHANGE:` paragraph in the commit **body** (the body, not the subject).

Because the releasable-commits check (§1) only inspects commit **subjects**, a breaking change MUST be carried by a `feat:`/`fix:` commit. A `BREAKING CHANGE:` note on any other commit type (e.g. `refactor:`) will never be released.

### 2.4 Examples

| Message | Effect |
|---|---|
| `feat: add Java project scaffold` | releasable; minor bump |
| `fix: correct dependency range in .projenrc.ts` | releasable; patch bump |
| `feat!: remove deprecated option X` | releasable; major bump |
| `fix!: change default of option Y` | releasable; major bump |
| `docs: update publishing guide` | **not releasable** — no release unless the window also has a `feat:`/`fix:` |
| `ci: pin node version` | **not releasable** — no release unless the window also has a `feat:`/`fix:` |
| `Updated the README` (no prefix) | **not releasable** |
| `chore(release): 0.0.1` (auto-generated) | never counted — filtered out of the window |

## 3. What a release run does

Per run, in order:

1. The `release` job runs `npx projen release` = `rm -fr dist` → **bump** (resolve latest tag → list releasable commits → if none, stop as no-op; if any, set the new version in `package.json`, write the changelog to `dist/changelog.md`) → **build** (jsii) → **unbump** → `git diff` must be clean. A build failure aborts the run before anything is published.
2. Gates: `tag_exists` (is the computed release tag already on origin?) and `latest_commit == github.sha` (did someone push a newer commit mid-run?).
3. If gated through, `Publish to npm` and `Publish to GitHub Releases` run in parallel:
   - **npm:** `publib-npm` with `NPM_TRUSTED_PUBLISHER=true` (OIDC, no token; see `spec/npm-publishing-setup.md`). A version that is already on the registry is reported as `SKIPPING: already published` — green, not an error.
   - **GitHub:** `gh release create vX.Y.Z --target <sha>` with the generated changelog as body; this also creates/pushes the `vX.Y.Z` tag.
4. The `chore(release): vX.Y.Z` commit (author `github-actions[bot]`) lands on `main`.

## 4. Rules

### MUST

- Type commits `feat:` or `fix:` when the change should be part of a release.
- Mark breaking changes with `!` or a `BREAKING CHANGE:` **body** paragraph, on a `feat:`/`fix:` commit (§2.3).
- Treat a push to `main` whose window contains `feat:`/`fix:` commits as an imminent release — review accordingly.
- Verify after each release: `npm view @xpertss/projen-types version` and the GitHub **Releases** page.

### MUST NOT

- Push a `feat:`/`fix:` commit to `main` unless you are ready to publish — the run it triggers will release.
- Edit `package.json` `version` by hand, or add a `version` field to `.projenrc.ts` — the release toolchain owns version numbers.
- Move, rename, or rewrite release tags (`vX.Y.Z`) on `main` — the tag is the version baseline.
- Force-push `main` — it desyncs the tag baseline from history.
- Edit `.github/workflows/release.yml` directly — edit `.projenrc.ts` and run `npx projen`. In particular, renaming the workflow file or changing the `release_npm` job would orphan the npm **trusted publisher** configuration (see `spec/npm-publishing-setup.md`, step 3).

### SHOULD

- Use **squash merge** for PRs and make the *squash title* the conventional message — it replaces all underlying commit subjects and therefore decides whether the merged change is releasable.
- Use the imperative mood in the subject; one logical change per commit; subject ≤ 72 chars.
- Keep a releasable (`feat:`/`fix:`) commit in the window whenever you intend a release to include a given set of changes; otherwise bundle the changes into a `feat:`/`fix:` PR.

## 5. Edge cases and known behaviors

| Situation | Outcome |
|---|---|
| Push to `main` with `feat:`/`fix:` commits in the window | release run — minor / patch / major per §2.2 |
| Push or manual run whose window has only non-releasable commits (`docs:`, `ci:`, …) | no-op run — green, nothing published |
| Window contains `feat:` (no breaking) | minor bump (highest level wins) |
| Breaking change marked per §2.3 on a `feat:`/`fix:` commit | major bump |
| Run with no commits since the last release tag (e.g. re-run of the same HEAD) | no-op run |
| Run for an already-published tag | `tag_exists` gate skips publishing |
| Version already on npm (e.g. published manually beforehand) | `publib-npm` prints `SKIPPING: already published`, run is green |
| Two runs in rapid succession | concurrency group serializes; the second run's `latest_commit` gate handles drift |
| Build fails | run aborts, no tag, no publish — fix and trigger again |
| `chore(release):` is the latest commit | excluded from the window — no double release |
